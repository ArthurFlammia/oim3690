The arc, in my own code

Ten entries, one per week. Every snippet here is lifted from that week's log, which means it's code I wrote and code I can explain.

WEEK 01

Setup, and seven lines of HTML

Got VS Code, Git, GitHub Desktop and Chrome working, put my personal site live, and made the oim3690 repo. The site itself came out of a prompt template from the slides, and what came back had things in it I hadn't asked for — a :root block declaring colors somewhere completely separate from where they got used. It took me a while to work out that var(--green) was pointing back up to it. The first thing I wrote by hand was the smallest page that counts as a page.

WEEK 02

More pages, and the idea of grouping

Added about-me.html and index.html to the course repo and started hunting for an MP1 client. This is the week I settled into a pattern I've used since: generate, then annotate. I wrote the skeleton of hello.html by hand, had AI build it out, then went through and commented every part — on the theory that if I couldn't write the comment I didn't actually understand the line.

WEEK 03

CSS, and my first real bug

Built css/styles.css and wrote rules by hand using all four selector types. This was also the week I caught something AI had done wrong: the CSS had been pasted inside about-me.html instead of into the stylesheet. Finding that taught me more than the rules did.

WEEK 04

Building for someone who isn't me

MP1: a three-page site for Platinum Pools. Flexbox put the service cards in a row and a media query stacked them on phones. The bigger lesson was non-technical — my client Vernon said it looked too plain and asked for photos, so I added a gallery and reworked the colors to match his branding. The first version being "done" and the first version being right are different things.

WEEK 05

Reading JavaScript before writing it

We were handed js-demo.html and told to figure out what it did. No writing, just reading. Working through the random background changer is where Math.random(), Math.floor() and array indexing finally clicked as three pieces of one idea.

WEEK 06

MP2: making a page do something

A tip splitter, in plain JavaScript. The thing I actually learned here was why Number() is not optional: input values come out of a form as text, so without converting them JavaScript glues them together as strings instead of adding them.

WEEK 07

The app starts remembering things

AI told me straight out that my tip splitter was too simple for MP2, which was fair. I rebuilt it around a history array so it keeps every split and shows a session total. This was the week I understood that the array is the app — the list on screen and the total are both just the array, drawn.

WEEK 08

MP3: talking to something that might not answer

Weather Now, built on the Open-Meteo API. Two requests that have to happen in order — city name to coordinates, then coordinates to forecast. I tested it by turning on airplane mode to make sure the failure path actually worked, which is a thing I would not have thought to do in week 4.

WEEK 09

Recipe Box: designing around an API's limits

My final project. The detail view broke first — I tried to render instructions off a filter.php result and got undefined, which is what sent me to the raw JSON. Turns out that endpoint only returns an id, a name and a thumbnail, and neither of TheMealDB's two search endpoints alone handles what people actually type. So I chained them: dish name first, and if that comes back empty, search the same word as an ingredient. The user gets one search box and never has to know there were two.

WEEK 10

Shipping, and the small stuff that matters

Demo Day, then cleanup. The detail view is a good example of what week 10 looks like versus week 5: TheMealDB stores ingredients as twenty separate numbered fields, most of them empty, so the list has to be rebuilt field by field and filtered — otherwise an 8-ingredient recipe renders twelve blank bullet points.

Questions that answered themselves

Every log ends with a question. Going back through them, some of the questions turned into the next project.

Asked in Week 07

"How do I make the saved splits stay there after the page refreshes? Right now all the data disappears when the browser reloads."

Answered in Week 08. Weather Now used localStorage to hold recent searches, and by Week 09 the whole favorites system in Recipe Box was built on it — JSON.stringify() going in, JSON.parse() coming back out.

Asked in Week 06

"Leaving a field blank or entering letters makes Number() return NaN. How do I check for invalid input and show a friendly message instead of a broken result?"

Answered in Week 08 and 09. Guard the bad input before it reaches the logic, and give the user a message that says what to do next — not "error," but "Try another word, like beef or rice."

Asked in Week 03

"When two CSS rules have the same specificity the later one wins — but how do I tell which selector is more specific without counting by hand?"

Answered by DevTools. The Styles panel shows overridden rules struck through. I stopped reasoning about specificity in my head and started just looking at it.

Asked in Week 08 · still open

"await geocodeCity(name) pauses until the API responds, but the page stays responsive the whole time. Where does the waiting actually happen?"

Still open. I understand what await does well enough to use it and not at all well enough to explain it, and that gap has bothered me for three weeks. It's the first thing I want to fix next.

What actually changed

The code got longer, but that isn't the real difference. In Week 1, when AI handed me a file, I read it to check whether it looked right. By Week 9 I was reading it to find where it would break — and testing for that on purpose, with airplane mode on and nonsense words in the search box. The bug I'm proudest of catching didn't throw an error at all: TheMealDB returns {"meals": null} with a 200 when nothing matches, so nothing crashed and nothing rendered. It just silently did nothing. I only found it because I went looking.

Where I've landed on AI: it's good at getting a structure onto the page from material I've already produced, and bad at sounding like me. The editing pass isn't optional cleanup — it's most of the work. This page is a fair example. It was drafted from my logs/ folder and then I rewrote the parts that weren't mine.

The other thing I'd tell myself in Week 1: "it works" isn't the finish line. Vernon saying the pool site looked too plain in Week 4, and rewriting the empty state in Week 10 so it says "try beef or rice" instead of "no results" — those are the same lesson showing up six weeks apart.
